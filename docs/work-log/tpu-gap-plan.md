# TPU gap: plan

Branch `feat/tpu-gap`, from `main` at `0d8aa3d9` (2026-10-25). The source of every item is
[torch-tpu-capability-gap.md](torch-tpu-capability-gap.md): the gaps to TorchTPU that can be built
and checked without a TPU. Items that only a TPU can prove are marked **unverified on TPU**.

## Results

Measured on the GB10 unless marked otherwise.

| # | Item | Status | Result |
|---|---|---|---|
| 1 | Multi-device | done | `scripts/pjrt-cpu-plugin/build.sh` builds `pjrt_c_api_cpu_plugin.so` at the XLA commit of the vendored headers (`d8679698`, jax 0.12.0.1), 12,313 Bazel actions. `CpuClientOptions` (`cpu_device_count`), `PjrtBinaries.cpuPluginPath`, `PjrtLoadedExecutable.executeOnDevices`, the shardings extension (`parameterShardings`, `outputShardings`), `OpShardingLayout` (tiled, replicated, partially replicated, iota assignments). `PjrtSession.runPerDevice` and `runSharded`. `PjrtMultiDeviceCpuTest`: all-reduce (one group and two), all-gather + reduce-scatter, a data-parallel gradient against the full batch, a row-sharded program and its gradient, and a matmul sharded on a 2 × 2 mesh, on 4 host devices, all equal to the interpreter. The multi-process key-value store is not testable with this plugin (it has no distributed options). |
| 2 | Rematerialization | done | `OPTIMIZATION_BARRIER(x, anchors…)` on every surface (interpreters, VJP, JVP, vmap, emitter, host rendering). `DxirRemat.apply(gradient, policy)`: saved values and parameters feeding a recomputation pass through a barrier anchored at the backward step that needs it; values recomputed for one backward step are re-barriered when a later one reads them. Results are bit-equal in the interpreter. GB10: 12 MLP blocks (4096 × 256, hidden 1024) 312 → 184 MiB; an 8-layer CausalLM step (d 512, 4 × 512 tokens) 1,036 → 512 MiB with block outputs as checkpoints (`SAVE_MARKED`, the `withRemat` default), 260 → 330 ms. `SAVE_DOTS` saved nothing on XLA:GPU. |
| 3 | Chunked LM head | measured, not built | XLA:GPU already fuses the softmax difference into the head-weight gradient GEMM: the whole-logits step's temporary buffer is 10 MiB (d 64) and 71 MiB (d 512) for 2,048 × 32,768 logits. The chunked form, with each chunk's logits recomputed, held 6 head-weight partial gradients at once: 450 MiB. Found on the way: a step differentiated its one-hot targets (`[rows, vocab]`); targets are now constants (`DxirReverseTransform(constantParams)`), 817 → 657 MiB on that step. |
| 4 | Device optimizers, accumulation, examples | done | `DeviceOptimizerStep` (state slots, scalar operands, `initialState`), with `DeviceAdamWStep` on it. `withDeviceSGD`: the host SGD's first-visit seed `v = g` is the scalar pair `a = 0, b = 1` of `v' = a·v + b·g`, so one program serves every step. `Muon` (host, PyTorch's update with an f32 Newton–Schulz iteration, AdamW for the other parameters, checkpointable) and `withDeviceMuon` (the iteration unrolled). `withGradientAccumulation(n)`: the step inlined `n` times (`DxirInline`, region-aware), mean loss and gradients, each microbatch's inputs behind a barrier on the previous sums. Interpreter: device SGD and device AdamW over LoRA adapters equal the host loops bit for bit, device Muon within 1e-5, Muon within 1e-5 of `torch.optim.Muon` (f32 iteration), accumulation equal to the mean of separate runs bit for bit. GB10: device SGD and Muon within 1 % of their host loops over 12 steps (Muon 4.23 → 1.68, SGD → 3.37); a 4-layer CausalLM over 8 × 256 tokens peaks at 508 MiB as one batch, 256 MiB as 4 microbatches in sequence, 467 MiB without the barriers. `examples/fine-tune` and `examples/lora-finetune` run AdamW in the step: LoRA 6 steps at a median 82 ms (the host loop's README: 320 ms), the same six answers to the training questions. Found on the way: XLA:GPU's v2 GEMM fusions drop a transpose from a dot operand at the vendored XLA commit, which gives wrong gradients on `main` (the LoRA example stalls near loss 1 with the host optimizer too); a CUDA `PjrtSession` compiles with them off (`CompileOptions.withXlaGpuFixes`, FOLLOWUPS §16). |
| 5 | Collectives and the ragged dot | done (ragged all-to-all not built) | `ALL_TO_ALL` and `COLLECTIVE_PERMUTE` (`CollectiveAttrs`) on every surface: both interpreters (the one-process view), tangents, VJPs (an all-to-all with its two dimensions swapped, a permute with its pairs reversed), `stablehlo.all_to_all` / `stablehlo.collective_permute`, the duality table. VJPs for `ALL_GATHER` and `REDUCE_SCATTER` (each other). On 4 host devices (item 1): all-to-all and permute move the right values, and the gradients of all-gather, reduce-scatter (one group and two), all-to-all (two axes and one) and permute satisfy the adjoint identity `Σ⟨f(x), w⟩ = Σ⟨x, f*(w)⟩` to 1e-5. `RAGGED_DOT` (`RaggedDotAttrs`), the grouped matmul: `rows` (`[M,K]` × `[G,K,N]`) and `contraction` (`[M,K]` × `[M,N]` → `[G,K,N]`), whose gradients are products of the two forms, emitted as `chlo.ragged_dot`; f64 gradients and tangents match central differences to 1e-8; on the GB10 both forms, and the gradient of a grouped two-layer MLP, match the interpreter (1e-5, 1e-4). Ragged all-to-all is not built: the XLA CPU backend has none and one GPU cannot run a group larger than one. `MOE_EXPERTS` stays inference-only; a trainable MoE layer is `RAGGED_DOT` after sorting rows by expert, not yet written. |
| 6 | Mosaic kernels in Kotlin | done, **unverified on TPU** | `mosaicKernel { }` (`MosaicKernelDsl.kt`): a grid with dimension semantics, input / output blocks with index maps over the grid indices (fixed blocks marked `synchronous`, as Pallas marks them), VMEM scratch, and a body of whole-block operations (loads and stores, elementwise ops with `jnp` broadcasting, scalar constants, `exp` / `rsqrt` / `tanh` / `log`, reductions keeping the axis, `dot` in its three transposes, casts, iota, compares, `where`, `pl.when`), each emitting what Pallas lowers for its `jnp` / `pl` counterpart. `MosaicTiledMatmul` is now written with it and still equals Pallas's module. `KernelScope` is a PTX instruction builder, so the DSL is a separate tile-level one. `harness/python/check_mosaic_kernels.py` (run by `MosaicKernelsTest` when a Python with Pallas is found) checks each kernel against its Pallas twin: the same module after `cse`, the serialized form equal to `mosaic-serde`'s, and the twin's values against numpy in TPU interpret mode (`pltpu.InterpretParams`). Row softmax (21 ops) and gridded RMSNorm (29 ops) pass. |
| 7 | Mosaic flash attention | forward and backward done, **unverified on TPU**; ragged paged attention not built | Causal flash attention in the DSL: forward (86 ops: online softmax over key blocks, running max and sum 128 lanes wide, f32 accumulator), backward dK/dV (79 ops) and dQ (68 ops) from the log-sum-exp and `rowsum(dO ⊙ O)`; each equals its Pallas twin and the twins match numpy in interpret mode (output 4.9e-3, log-sum-exp 4.5e-7, gradients 1.2e-2, bf16 data). `MOSAIC_KERNEL` takes an optional `vjp` (operands, results, cotangents → gradients); the reverse transform inlines it, so a kernel with one is differentiable (without one it stays inference-only). `MosaicAttention.causalFlashAttention` emits the forward kernel with a vjp that calls the two backward kernels, every kernel with a DXIR reference: in the interpreter the gradients of a loss through it match f64 within 0.35 % of the largest value; for a TPU the gradient program is three `tpu_custom_call`s; on the GB10 the references run and match the interpreter. Found on the way: the emitter wrote −∞ and NaN in array constants as text MLIR rejects; they are bit patterns now. Ragged paged attention needs scalar prefetch, HBM refs, DMA and semaphores in the DSL; not built. |
| 8 | Portable serving path | done on CUDA, **unverified on TPU** | An artifact exported with CUDA kernels off (the default) and weights unquantized, int8 or FP8 has no `custom_call` in any entry body. `HfLlamaServingArtifactTest.thePortableArtifactCallsNoCustomKernelAndServesOnPjrt`: TinyLlama-1.1B in all three forms, served by the ctypes runtime on PJRT-CUDA with the weights in the PJRT pool, generates HuggingFace's 6 tokens in each. Found on the way: the Python runtime could not stage int8 or FP8 weights (`RAW_DTYPES` knew f32, i32 and bf16); it stages `i8`, `u8` and `f8e4m3fn` now. NVFP4 still always calls CUDA kernels (its dense matmul and MoE); `ServingModel` (the JVM path) still refuses quantized artifacts and hardcodes `PjrtTarget.Cuda`. |
| 9 | FP8 matmul | done | `FP8_MATMUL(a, b, aScale, bScale)` (`Fp8MatmulAttrs`): e4m3fn `[M,K]` × `[K,N]`, rowwise or tensorwise f32 scales, f32 or bf16 result, emitted as a `dot_general` on the f8 operands; interpreters, cost model, inference-only refusal under AD. GB10 (128 × 256 × 192) against the interpreter: 1e-5 (f32), 1e-2 (bf16). Whether XLA:GPU ran it on FP8 units was not checked. Found on the way: an FP8 Triton GEMM tiled 16 deep along K returns exactly twice the product on the GB10, and the autotuner picks that tile for this shape; a CUDA `PjrtSession` compiles a program with an FP8 dot with Triton GEMMs off (FOLLOWUPS §16). |
| 10 | 32-bit forms of i64 hot spots | not built | Both are 64-bit by specification: `NGRAM_HASH` multiplies with 64-bit wraparound and takes a signed remainder; the sampler draws with splitmix64 and keeps an i64 fixed-point prefix sum. Equal outputs in 32 bits need multi-limb arithmetic (a 64-bit product from 32-bit halves, a remainder of operands up to 2^31), and without a TPU what the i64 forms cost there cannot be measured. |
| 11 | Padded `set_dimension_size` in `BoundedProgram` | not built | `BoundedProgram` traces at static sizes with explicit masks, and the emitter writes static types. The padded form needs the dynamic type (`tensor<?x…, bounds>`) carried through every op that touches a bounded axis (elementwise ops keep it; reductions and contractions over it drop it), or XLA's dynamic padder cannot honour the size downstream: a type-propagation pass over the emitter's op kinds, not a wiring change. |
| 12 | Sharded safetensors | done | `ShardedCheckpoint` (`:core`): each rank writes `shard-<rank>.safetensors` of its blocks, each block's offsets and the global dims in the file's metadata; a reader assembles any block of any tensor from the shards that hold it, reading only those bytes (runs along the last axis), takes overlapping replicas from the first shard and refuses a block no shard covers. A 2 × 2 tiling read whole, as column halves and as a block across four shards; bf16 bit for bit. |
| 13 | Profiler | done | The plugin's profiler extension (`PJRT_Profiler_Extension`, `PLUGIN_Profiler_Api`): `PjrtClient.profile`, `PjrtSession.profile(trace) { … }` write a serialized XSpace (`*.xplane.pb`). GB10: 11.9 KB with the host, CUPTI, NVTX and `/device:GPU:0` planes and the kernels (`gemm_fusion_dot`, `loop_reduce_fusion`). Found on the way: the plugin's `collect_data` does not follow its header's two-call protocol; it serializes into its own buffer on the first call, as XLA's own reader assumes. |
| 14 | Executable cache | done | `PjrtExecutableCache(dir, maxBytes, shared, publish)`: least-recently-used eviction to `maxBytes` after each write (a hit refreshes an entry; entries whose lock another caller holds stay); a shared directory read on a local miss and copied in, written to with `publish`; `TLALOC_PJRT_CACHE_MAX_BYTES`, `_SHARED_DIR`, `_PUBLISH`. GB10: a cache bounded to 2.5 entries evicts the oldest of three, and a second "machine" with an empty local cache loads the first one's published entry. |
| 15 | TPU specs, MFU | done | `DeviceDescriptors`: v5e and v6e corrected to Google's spec pages (v6e 918 TFLOPs, 1638 GB/s; v5e 800 GiB/s), v5p (459 TFLOPs, 2765 GB/s) and v7 / Ironwood (2307 bf16 and 4614 FP8 TFLOPs, 7380 GB/s, 192 GiB) added, VMEM from TorchTPU's table; `forDeviceKind` maps PJRT device kinds (`TPU v5 lite`, `TPU7x`, …). `StepBenchmark.Result.utilization(device, flopsPerStep, bytesPerStep)`: FLOP/s and MFU at the median step, bytes/s and MBU, written into `toJson`. |
| 16 | Docs that disagree with the code | done | `DISTRIBUTED.md`: the five collectives with their adjoints, `PjrtSession` on several (host) devices, the XLA CPU plugin tests. `TPU_MEGAKERNELS.md` "Not done": grids (the DSL), the DSL kernels, gradients through a kernel's `vjp`. The vLLM-TorchTPU work log dates its "verification-only"; the 2026-09-21 readiness audit points to the capability gap. `TPU_BRINGUP.md` already lists both TPU suites (5 smoke + 7 Mosaic). |
